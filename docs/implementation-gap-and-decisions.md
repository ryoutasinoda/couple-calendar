## 1. 調査結果の見方

- **実装済み**: 要件を満たす主要な処理がコード上に存在する
- **部分実装**: 一部の処理は存在するが、要件の操作・表示・検証まで完了していない
- **未実装**: 現行コードに該当する処理がない
- **未確定**: 実装前に利用方針または運用方針を決める必要がある

今回の調査では、v4を現行の正規要件とし、旧要件・`yoken2.md`との矛盾も記録する。現行スタックは React + Vite + Cloudflare Pages/Functions + Workers + D1 を継続する前提とする。

## 4. 仕様書間の不一致

| 論点 | 文書間の状態 | 現行方針と確認事項 |
|---|---|---|
| 技術スタック | `yoken2.md`はNext.js + Supabase + Vercelをたたき台として記載。v4はCloudflare維持を前提 | 現行Cloudflare構成を継続することでよいか、最終決定を記録する |
| 日付タップ | 旧要件は直接追加、v4は一覧表示後の追加を統合案として記載 | 日付セルタップ時の最終操作を決める |
| 未確定事項 | `yoken2.md`は「特になし」、v4は複数の要確認事項を記載 | v4の第13章を優先し、決定済み・未決定を別管理する |
| 通知 | 必須要件だが、送信時刻・当日通知・送信基盤は未定義 | 最低限「前日通知のみ」から始めるか、当日通知も同時に実装するか決める |
| 周期終了 | 自動区切り＋手動補正が要件 | 現行の60日補助終了は暫定値であり、医療記録上の意味を確認する |
| 自己検査 | 種類は排卵・妊娠の2つで確定。日時記録が要件 | 基礎体温を追加しない方針は維持し、時刻の入力粒度を決める |
| 記録の共有 | 予定には`shared`があるが、生理・周期・自己検査の共有範囲が明示されていない | 妊活記録は常に夫婦共有か、記録ごとに個人設定できるか決める |

## 5. 実装前に決めるべき事項

### 5.1 最優先の意思決定

1. **通知の最小仕様**
   - 通知対象: `notify_before_day`が有効な予定のみか
   - 通知時刻: 前日の何時か。Asia/Tokyo固定か、ユーザー設定か
   - 当日通知を実装するか
   - 同じ予定を夫婦それぞれへ送るか、作成者だけへ送るか
2. **周期・生理の編集ルール**
   - 開始日・終了日の過去編集を許可するか
   - 60日自動終了を正式仕様にするか、暫定表示だけにするか
   - 周期の分割・統合を本当に必要とするか
   - 治療法の候補と自由入力のどちらにするか
3. **妊活記録の共有範囲**
   - 生理期間、周期、自己検査、メモ、金額を常に共有するか
   - 個人記録を許可する場合、各テーブルに`shared`または作成者制御を追加するか
4. **現行Cloudflare構成の正式採用**
   - Next.js/Supabaseへ移行しないことを決定事項として残すか
   - Cloudflare無料枠とD1のバックアップ・通知運用を許容できるか

### 5.2 決定済み通知仕様

- 通知は前日のみ、Asia/Tokyo 09:00に送信する
- 共有予定は`target`が`husband`/`wife`の場合は該当役割、`both`の場合は夫婦双方へ送信する
- 非共有予定は作成者本人のPush購読だけへ送信する
- 410/404等で無効と判定されたPush購読は自動削除する
- 本番環境では`VAPID_PUBLIC_KEY`と`VAPID_PRIVATE_KEY`をWorker Secretとして設定する

### 5.3 実装開始前に最低限確認するデータ仕様

- 日付と時刻はAsia/Tokyo基準で統一する
- 金額は整数の日本円、0円を許可するか、上限を設けるか
- カテゴリ削除後も既存予定を表示できるようにするか
- 予定の`target`と`shared=false`の関係をどう扱うか
- 予定・周期・自己検査を削除した場合の関連データの扱い
- アカウント退会時のD1データ、Push購読、Cookieセッションの削除範囲
- エクスポート形式、ファイル暗号化の要否、インポート時の重複判定

## 6. 推奨する開発順序

### Phase 0: 仕様確定・基盤整理

- 上記5.1の4項目を決定し、この文書の「決定事項」へ反映
- `schema.sql`とWorkerの起動時スキーマ補完をmigrationへ整理
- APIの所有権・入力検証・認証強度を強化（認証強度は実装済み）
- 本番・ローカルの環境変数、VAPID鍵、D1環境を分離

### Phase 1: 要件の見える差分を埋める

- 生理期間のカレンダー表示
- 予定フォームの場所、金額、前日通知、周期紐付け
- 自己検査の時刻入力・編集
- 周期の治療法・境界編集と詳細表示
- カテゴリ編集

### Phase 2: 通知を実運用可能にする

- Cronまたは採用した実行基盤を設定
- 通知対象の抽出、送信履歴、失敗時の扱いを実装
- 無効なPush購読の削除
- iOS Safari / Android Chromeで許可から受信まで確認

### 次に着手する順序

1. **Push通知の本番有効化**: VAPID鍵を設定し、iOS/Android実機で購読・前日受信・無効購読削除を確認する
2. **認証運用の補強**: ログイン試行制限、セッション失効、パスワード変更を追加する
3. **データ復元**: JSONインポートは重複判定と上書き確認を設計してから実装する
4. **共有範囲の確定**: 生理・周期・自己検査を常時共有とするか、個人記録にするか決める

### Phase 3: データ保全と品質確認

- エクスポート・バックアップ・削除方針の実装
- モバイル実機テスト、アクセシビリティ確認
- 認証・権限・個人情報のセキュリティ確認
- 本番D1 migration、復旧手順、監視の確認

## 8. 現時点の結論

現行実装は、カレンダーと夫婦共有の基盤に加えて、カテゴリ・生理・周期・自己検査のデータモデルまで進んでいる。次の主作業は新しい基盤を作ることではなく、v4で明示された表示・入力・編集体験を完成させ、Push通知を実際の定期送信へ接続し、APIの入力検証と認証強度を本番利用水準へ引き上げることである。

特に、通知、周期の自動終了、妊活記録の共有範囲、Cloudflare構成の正式採用は、実装者の判断だけで確定させず、先に合意を取る。
