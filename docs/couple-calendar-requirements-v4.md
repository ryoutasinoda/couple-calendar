# Couple Calendar（夫婦向け不妊治療・予定管理カレンダー）要件定義書 v4

> 本ドキュメントは `couple-calendar-requirements.md`（旧要件）と、妻が希望する要件（`yoken2.md`）を統合し、差異を整理した正式版です。
> 変更点・要確認事項は各セクションに明記しています。

## 0. 本バージョンでの主な変更点（旧要件からの差分）

### 0.1 機能追加・具体化（旧要件と矛盾しないもの）

| 項目 | 旧要件 | 今回追加・変更 |
|---|---|---|
| 生理期間の表示 | 「血液を直接連想させない」程度の方針のみ | 開始日〜今日を斜線+破線で「未終了」表示、開始日は三日月アイコン、終了記録で塗りつぶしに切替 |
| 治療周期（サイクル）管理 | なし | 生理開始日を基準に自動区切り＋手動補正。周期ごとに治療法・結果（陽性/陰性）・回数サマリーをカード表示 |
| 自己検査記録 | 「妊娠検査」という予定種別のみ | 排卵検査薬／妊娠検査薬を区別し、1日複数回・結果（陰性/陽性/判定中）を記録 |
| 費用記録 | なし | 予定・記録に金額を任意入力できる簡易記録（集計機能は範囲外） |
| カテゴリのカスタマイズ | アイコンは固定セット | 色・アイコンをユーザーが自由にカスタマイズ可能に変更 |
| 予定ごとの共有設定 | target（husband/wife/both）で対象者指定のみ | 予定ごとに「パートナーと共有」on/offを明示的に選択可能に |
| 通知 | 優先度D（将来検討） | 必須要件に格上げ。Web Push対応、iOSはPWA化（ホーム画面追加）を案内 |
| PWA化 | 優先度D（将来検討） | 通知要件と合わせて前提要件に格上げ |

### 0.2 要確認・要すり合わせ事項（矛盾・方向性の違い）

- **技術スタック**：現行実装（Vite + React + TypeScript / Cloudflare Pages + Workers + D1 / 独自Cookieセッション認証）は、iPhone Safariでのログインまで含めてすでに動作確認済み。一方、妻の要件書は Next.js / Supabase / Vercel という別スタックをたたき台として提示している。**本ドキュメントでは現行のCloudflareスタックを維持する前提で記載する**（詳細は第9章）。フルリライトを希望する場合は別途判断が必要。
- **サービスの主従関係**：旧要件は「汎用の夫婦カレンダー（妊活は一部）」、妻の要件書は「不妊治療記録サービス（カレンダーは一部機能）」。本ドキュメントでは、既存のカレンダーを土台に、不妊治療記録機能を主要機能として統合する構成とする。

## 1. プロジェクト概要

- **目的**：夫婦2人で、日常の予定に加えて不妊治療の通院・治療スケジュールと、生理周期・自己検査などの記録を共有しながら管理する
- **対象**：自分と妻の2人（世帯単位。用語は旧要件の「me/wife」を踏襲する）
- **対応端末**：iPhone / Android（スマートフォンのブラウザで利用できるPWA）
- **想定ユーザー数**：夫婦1組のみ
- **費用**：可能な限り無料で運用
- **開発方針**：Cloudflareを中心とした無料または低コスト構成を優先（既存実装を活かす）
- **UI方針**：妻が使いやすく、見た目が整った、シンプルで親しみやすいデザイン

---

## 2. アカウント・共有

- 本人・パートナーそれぞれが専用アカウントでログイン（ログインID＋パスワード方式、パスワードはハッシュ化して保存）
- 同じ予定・記録を両アカウントで閲覧・編集可能
- **【新】予定ごとに「パートナーと共有」のon/offを設定可能**（offの場合は本人のみ閲覧・編集可能な個人記録として扱う）
- 招待コード方式でパートナーを紐付ける（既存実装を踏襲）

---

## 3. 画面構成

### 3.1 カレンダー（ホーム画面）

- 月間カレンダーを基本表示
- 月の前後移動、「今日」ボタンで現在月・現在日に戻る
- 今日の日付・土日を視覚的に区別
- **【新】各日付セルに、その日の予定カテゴリをアイコン＋淡い背景色で表示**
- 日付タップで、その日の予定一覧を表示（旧要件：新規追加モーダルを開く／新要件：一覧を下部表示 → **統合案：日付セルタップで一覧を表示し、一覧内の「＋」または空欄タップで新規追加モーダルを開く**。この画面遷移の詳細はモックアップで別途すり合わせる）
- 右下に予定追加ボタン（＋）を新設
- 既存予定をタップすると編集モーダルを開く
- 予定ボタン側ではイベント伝播を停止し、日付セルの新規追加処理と競合しないようにする（既存方針を維持）

### 3.2 予定の新規登録

- カテゴリをアイコン付きカードで選択：診察／注射（通院）／自己注射／服薬／移植／生理／その他（＋ユーザーが自由にカテゴリを追加可能）
- 日付・時刻・場所（病院名）・メモを入力
- 「前日に通知」「パートナーと共有」のon/off
- **生理を選択した場合は専用フロー**：
  - 未記録時：「開始を記録」ボタンのみのシンプルな画面
  - 開始記録済みの場合：「終了を記録」ボタンに切り替え

### 3.3 治療記録一覧（周期ごと）

- 「周期」単位でカード表示（第1周期、第2周期…）
- 各カードに表示する情報：
  - 治療法（タイミング法／人工授精／体外受精 など）
  - 期間（開始日〜終了日、進行中は「〜」で終了日未定を表現）
  - ステータスバッジ（進行中／終了）
  - 通院・自己注射などの回数サマリー
  - 終了した周期は結果（陽性／陰性の2択のみ、詳細な数値は記録しない）を表示
- カードタップでその周期内の予定・記録詳細に遷移

### 3.4 自己検査の記録

- 種類：排卵検査薬／妊娠検査薬（カテゴリは今後追加できる想定）
- 結果：陰性／陽性／判定中
- 日時・メモを記録
- 1日に複数回の記録に対応（同じ日の記録は一覧で下に並べて表示）

---

## 4. 生理期間の表示仕様

- 開始日を記録した時点で、開始日〜今日を「未終了（現在まで）」の期間として自動表示
  - 見た目：斜線パターン＋破線枠で控えめに表現（過度に直接的な表現は避ける）
  - 開始日のマーク：三日月アイコン（雫マークのような直接的な表現は避ける）
- 終了日を記録すると、開始日〜終了日が確定期間として塗りつぶし表示に切り替わる

---

## 5. 周期（サイクル）の区切り方

- 基本は自動区切り：生理開始日を基準に、次の生理開始日の前日までを1周期とする
- 懸念点と対応方針

| 懸念点 | 対応方針 |
|---|---|
| 生理が来ない周期（妊娠判定待ちなど）がいつまでも終了しない | 一定期間経過、または妊娠判定の記録をもって自動終了とする補助ルールを設ける |
| 生理不順で開始日の記録が数日ずれる／記録を忘れる | 開始日を後から編集できるようにする |
| 治療を一時中断した期間も1周期として数えてしまう | 手動で周期の境界を分割・統合できる補正機能を用意する |

- 自動区切り＋手動での境界編集をハイブリッドで採用する

---

## 6. カテゴリ要件

- カテゴリはユーザー（世帯単位）が自由に色・アイコンをカスタマイズ・追加可能（旧要件の「固定アイコンセット」から変更）
- 初期プリセット：診察／注射（通院）／自己注射／服薬／移植／生理／その他
- 旧要件の日常カテゴリ（デート／仕事／買い物）も初期プリセットとして維持する（妻の要件書では明記されていないが、旧要件の日常予定管理という目的を損なわないため継続）
- 要件の共通方針（旧要件を踏襲）：
  - アイコンとテキストを両方表示
  - 色を増やしすぎない
  - 予定全体をタップできる設計を優先し、アイコン単体の小さなタップ領域を乱立させない
  - 生理関連アイコンは血液を直接連想させる見た目を避ける

---

## 7. 費用記録

- 通院・治療にかかった金額の簡単な記録に対応
- 家計簿アプリとの連携は行わず、サービス内で完結するシンプルな記録機能とする
- 予定・記録に金額欄を任意で入力できる程度の位置づけ（詳細な費用管理・集計機能は範囲外）

## 9. 技術方針

### 9.1 現行実装（維持する前提）

- フロントエンド：React + TypeScript + Vite、Cloudflare Pagesでホスティング
- バックエンド：Cloudflare Workers（`couple-calendar-api`）
- DB：Cloudflare D1
- 認証：ログインID＋パスワード（ハッシュ化）、Cookieセッション方式（`SameSite=None; Secure`）
- フロント・API間はCloudflare Pages Functions（`functions/api/[[path]].ts`）による同一オリジンプロキシ経由（iPhone Safariのサードパーティ Cookie 制限対策として導入済み）

### 9.2 妻の要件書で提案されていた構成（不採用、参考記録として残す）

- フロントエンド：Next.js（PWA対応）
- バックエンド/DB/認証：Supabase（PostgreSQL＋認証＋リアルタイム同期）
- ホスティング：Vercel
- プッシュ通知：Web Push API

### 9.3 今後の対応

- 上記9.1の現行スタックを維持し、9.2で挙がった「PWA化」「Web Push通知」「Supabaseのリアルタイム同期」に相当する機能は、Cloudflareの構成内（Workers Cron、Web Push APIの自前実装など）で代替できないか検討する
- リアルタイム同期（Supabaseの特徴の一つ）が本当に必要か（＝ポーリングや手動更新で十分か）は要確認

## 10. データベース設計（現行D1スキーマの拡張案）

現行の `schema.sql`（users / sessions / couples / couple_members / events）をベースに、以下のテーブルを追加する想定。カラム名・型は既存スキーマ（SQLite/D1、TEXT/INTEGER中心）の書式に合わせている。

```sql
-- カテゴリ（カスタマイズ対応）
CREATE TABLE IF NOT EXISTS categories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  couple_id INTEGER NOT NULL,
  name TEXT NOT NULL,
  icon TEXT NOT NULL,
  color TEXT NOT NULL,
  is_default INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);

-- 生理期間
CREATE TABLE IF NOT EXISTS period_records (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  couple_id INTEGER NOT NULL,
  start_date TEXT NOT NULL,
  end_date TEXT, -- NULLなら未終了（今日まで表示）
  created_at TEXT NOT NULL
);

-- 治療周期
CREATE TABLE IF NOT EXISTS cycles (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  couple_id INTEGER NOT NULL,
  start_date TEXT NOT NULL, -- period_recordsのstart_dateから自動生成
  end_date TEXT,
  treatment_type TEXT, -- タイミング法 / 人工授精 / 体外受精
  result TEXT, -- '陽性' / '陰性' / NULL（未確定）
  is_manual_override INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);

-- 自己検査
CREATE TABLE IF NOT EXISTS self_tests (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  couple_id INTEGER NOT NULL,
  cycle_id INTEGER,
  type TEXT NOT NULL, -- '排卵検査薬' / '妊娠検査薬'
  result TEXT NOT NULL, -- '陰性' / '陽性' / '判定中'
  tested_at TEXT NOT NULL,
  memo TEXT,
  created_at TEXT NOT NULL
);
```

既存の `events` テーブルへの拡張案：

```sql
ALTER TABLE events ADD COLUMN category_id INTEGER; -- categoriesへのFK（icon文字列から移行）
ALTER TABLE events ADD COLUMN cycle_id INTEGER; -- cyclesへのFK（nullable）
ALTER TABLE events ADD COLUMN amount INTEGER; -- 費用記録（nullable）
ALTER TABLE events ADD COLUMN shared INTEGER NOT NULL DEFAULT 1; -- パートナー共有on/off
ALTER TABLE events ADD COLUMN notify_before_day INTEGER NOT NULL DEFAULT 0; -- 前日通知
```

**設計メモ**
- `cycles` は `period_records` の開始日をトリガーに自動生成し、次の開始日が来たら前の周期の `end_date` を自動セットする（自動区切り＋手動補正の要件に対応）
- `events.amount` で「簡単な金額記録」をカバーし、専用の費用テーブルは設けない
- `categories` は既存の `icon TEXT` 列挙型から、`couple_id` 単位でカスタマイズ可能なテーブルに移行する（既存データの `icon` 文字列との互換性維持が必要、詳細はマイグレーション設計時に検討）

## 11. 開発ルール（既存を維持）

1. 既存機能を壊さないこと
2. TypeScriptの型安全性を維持すること
3. Reactのstate管理を分かりやすく保つこと
4. スマートフォン操作を優先して設計すること
5. 予定ボタンと日付セルのイベント伝播に注意すること
6. 変更範囲を必要最小限にすること
7. UIを変更する場合は、PC表示とスマートフォン表示の両方を確認すること
8. 既存データ（D1）との互換性を維持すること（マイグレーションは既存レコードを壊さない設計にする）
9. 不明な仕様を勝手に決めず、必要なら確認事項として明示すること
10. 実装後は、TypeScriptエラー・ビルドエラー・操作上の問題を確認すること
11. **【新】認証・DBスキーマ変更・技術スタックの変更など不可逆性が高い処理は、実装前に確認すること**
