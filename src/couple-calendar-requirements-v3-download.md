## 1. プロジェクトの目的・前提

- 夫婦2人で利用する無料または極力低コストのカレンダー。
- 主目的は妊活・不妊治療関連の予定管理。
- デート、仕事、買い物など一般予定も同じカレンダーで管理。
- iPhone・Androidのスマートフォン中心。
- PWAとして利用する想定。ブラウザからアクセスし、ホーム画面に追加する。
- PCブラウザでも最低限使えるレスポンシブUI。
- 不特定多数への公開や大規模サービス化は想定しない。
- 予期せぬ課金を避ける。有料サービス・従量課金が必須になる場合は事前確認。
- 妊活・医療関連情報を扱うため、セキュリティ・プライバシー・アクセス制御を重視。

1. 夫婦2人が迷わず操作できること

- 夫：淡い青
- 妻：淡いピンク

- 色はカテゴリではなく対象者を表す。
- 色だけに依存せず「夫／妻／両方」の文字やアイコンでも明示。

注意：
- 現在の簡易実装では`me`／`wife`の2択。
- 将来の共有版では`husband`／`wife`／`both`の3値を扱う設計。

## 6. イベントデータ

### 6.1 将来の共有版モデル
日付・時間を一体化したDateTimeではなく、以下を分離する。
- `start_date`
- `end_date`
- `start_time`
- `end_time`
- `is_all_day`
- タイムゾーン：`Asia/Tokyo`
- 日付：`YYYY-MM-DD`
- 時間：`HH:mm`

日付のみ：
- `start_date`あり
- `end_date`なし
- `start_time`なし
- `end_time`なし
- `is_all_day=false`

終日：
- `is_all_day=true`
- `start_time`と`end_time`は空

複数日：
- `start_date`を開始日
- `end_date`を終了日

### 6.2 イベント項目
- タイトル
- 対象者
- 日付
- 開始・終了時刻
- 終日
- 複数日
- カテゴリ
- 場所
- メモ
- アイコン
- 作成者
- 作成日時・更新日時（共有版）

ルール：
- タイトル必須。空白のみは禁止。
- タイトル省略時に「予定」とする案。
- 場所はメモと分離。
- メモは自由入力。妊活の補足、持ち物、体調、医師の指示などに利用。
- 過去予定は削除しない限り残す。
- 終日予定では時間を空にする。
- 終了時刻が開始時刻より前なら保存しない。
- エラー原因と修正方法を表示。
- 予定／実績の区別は設けない。
- 完了チェックは設けない。
- 繰り返し予定はMVP対象外。
- コピー機能、写真、イベント変更履歴はMVP対象外。

### 6.3 現在の簡易実装
現在のTypeScriptモデルは`me`／`wife`、単一の`date`を中心とする簡易版。
共有版へ移行する際には、複数日・場所・カテゴリ・作成者・両方対象などを追加する必要がある。
既存localStorageキーは理由なく変更しない：
- `couple-calendar-events`

## 9. AI機能全般

AIはチャットだけでなく、予定登録・検索・整理を補助する。
候補：
- 自然文から予定下書き生成
- 登録済み予定の自然文検索
- 日付・期間で検索
- 妊活予定の整理
- 登録前の確認・修正
- カレンダー情報に基づく候補提示

最重要：
- AIは直接DBを書き換えない。
- AIは構造化データを返すだけ。
- Workersがバリデーションし、ユーザー確認後に通常の保存処理を行う。
- AIが生成したSQLを直接実行させない。
- AIの回答・提案・下書きと、確定保存済みデータを明確に区別。

基本フロー：
1. 自然文入力
2. AI解析
3. 構造化データ生成
4. Workers側バリデーション
5. 確認画面
6. ユーザーが全項目を編集
7. ユーザーが保存またはキャンセル
8. 通常の保存APIでDB更新

安全方針：
- AIが存在しない予定を作らない。
- AIの推測結果とDB／localStorageの実データを混同しない。
- AIへ全予定を無制限に送らない。
- 可能な限り期間・対象者などで先に絞り込む。

## 15. 認証・夫婦共有

### アカウント
- 夫婦それぞれが個別アカウント。
- 好きなログインID＋パスワード。
- 表示名必須。
- パスワードは平文保存しない。
- 認証情報をソースコードに書かない。
- Cookieセッションを想定。
- HttpOnly、Secure、有効期限あり。
- 認証情報をlocalStorageへ保存しない。

### MVP対象外候補
- ログアウトUI/API
- パスワードリセット
- 夫婦解除

### 共有
- 夫婦で1つの共有カレンダー。
- 原則すべて相互共有。
- 他の利用者のデータへアクセス不可。
- サーバー側で所属夫婦・権限を検証。

### 参加フロー
作成側：
1. アカウント作成
2. カレンダー作成
3. 自分の役割を夫／妻から選択
4. 招待コード発行
5. 相手へ渡す

参加側：
1. アカウント作成
2. 招待コード入力
3. 夫／妻を選択
4. 共有カレンダーへ参加

1夫婦につき：
- husband最大1人
- wife最大1人
- DBのUNIQUE制約で担保

## 16. 招待コード

確定している方針：
- 英数字のランダム文字列。
- 8～10文字程度。
- 0/O/1/I/lなど見間違えやすい文字は可能なら除外。
- 発行時のみ平文を表示。
- DBには平文ではなくハッシュを保存。
- 入力されたコードをハッシュ化して照合。
- 再発行時は旧コードを無効化。
- 参加後も必要に応じて再発行できる設計。
- パスワードと同様に秘密情報として扱う。
- ログや画面に不要に残さない。

要確認：
- 招待コードの有効期限を設けるか。
- 再発行権限を誰に与えるか。
- 参加済み後の再発行を許可する具体的画面。
- コード入力失敗回数の制限。

- 必要に応じてCloudflare Pages
- Cloudflare Workers AI
- PWA

基本経路：
- React → HTTPS → Workers
- Workersで認証・バリデーション・認可・AIオーケストレーション
- D1でデータ保存
- Workers AIで構造化処理

重要原則：
- フロントエンドからD1へ直接アクセスしない。
- Workersで認証・所属・権限を確認。
- APIキーをフロントへ埋め込まない。
- 外部AIへの送信データを最小化。
- 無料枠、利用制限、料金、ログ・学習利用を実装前に公式情報で確認。
- Cloudflare/Vite/Wranglerの手順は実装時点の公式ドキュメントを確認。

- `GET /api/categories`

AI：
- `POST /api/ai/parse`

- `GET /api/events?from=YYYY-MM-DD&to=YYYY-MM-DD`

## 22. 実装ルール

- 変更前に現在のソースコードを読む。
- 確定仕様を勝手に変更しない。
- 既存機能を壊さない。
- TypeScriptの型安全性を維持。
- スマートフォンのタップ操作を優先。
- 日付セルと予定ボタンのイベント伝播に注意。
- localStorageの既存データとの互換性を維持。
- PCとスマートフォンの両方で確認。
- AI下書きを確認なしで保存しない。
- AI検索結果として存在しない予定を表示しない。
- APIキー・パスワードなどをコードへ書かない。
- 認証、外部API、課金、大量削除などの重大変更は実装前に確認。
- 不明な仕様は独断で確定せず、選択肢とメリット・デメリットを示す。
- 実装後にTypeScriptエラー、ビルドエラー、操作上の問題を確認。
- 変更完了時は変更ファイル、変更内容、確認項目、残課題、ユーザーが実行するコマンドを報告。
