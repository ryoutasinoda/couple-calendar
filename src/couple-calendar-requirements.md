# Couple Calendar（夫婦向け妊活・予定管理カレンダー）設計要件

## 1. プロジェクト概要

夫婦2人で利用する、無料の予定・妊活管理カレンダーアプリ。

- 対象：自分と妻の2人
- 対応端末：iPhone / Android
- 利用形態：スマートフォンのブラウザで利用できるWebアプリを想定
- 想定ユーザー数：夫婦1組のみ。将来的に不特定多数へ公開する予定はない
- 費用：可能な限り無料で運用
- 開発方針：Cloudflareを中心とした無料または低コスト構成を優先
- UI方針：妻が使いやすく、見た目が整った、シンプルで親しみやすいデザイン

## 2. 開発環境・リポジトリ

- フレームワーク：React

## 3. アプリの主要目的

以下の情報を夫婦で一元管理する。

- 妊活に関する予定
  - 通院
  - 排卵誘発剤・注射
  - タイミングを取る日
  - フーナーテスト
  - 妊娠検査
- 日常の予定
  - デート
  - 仕事
  - 買い物
  - その他の予定
- 夫婦それぞれの予定を区別して表示
- 過去の記録を残し、後から確認できるようにする

## 4. ユーザー・権限

### 4.1 ユーザー

- `me`：自分
- `wife`：妻

予定ごとに、誰の予定なのかを保存する。

### 4.2 ログイン方針

将来的なログイン方式の希望：

- 夫婦だけが使うため、簡易的なログインでよい
- 「好きなID + パスワード」の形式を希望
- 不特定多数向けの複雑なアカウント管理は不要

※認証・データベースの実装方式は今後決定する。セキュリティ上、パスワードを平文で保存しないこと。

## 5. カレンダー要件

### 5.1 基本表示

- 月間カレンダーを表示
- 月の前後移動ができる
- 「今日」ボタンで現在月・現在日に戻れる
- 今日の日付を視覚的に強調
- 日曜日・土曜日を視覚的に区別
- スマートフォンでも操作しやすいレスポンシブUI

### 5.2 予定の表示

カレンダー上では、予定を以下の形式で表示する。

- アイコン + 予定タイトル
- 時刻はカレンダー上には基本的に表示しない
- 予定の詳細はタップして編集画面で確認
- 予定ボタンをタップした場合は、日付セルの追加処理が誤作動しないようにする
- 予定のメモは、必要に応じてタイトル属性や詳細画面で確認できるようにする

### 5.3 日付操作

- 日付セルをタップすると、その日付で新規予定追加モーダルを開く
- 既存予定をタップすると編集モーダルを開く
- 以前はダブルクリック方式だったが、スマートフォン操作を考慮し、日付セルは `onClick` を使用する
- 予定ボタン側ではイベント伝播を停止し、日付セルの新規追加処理が同時に発生しないようにする

## 6. 予定データ要件

予定は以下の情報を持つ。

```ts
type Member = 'me' | 'wife'

type EventIcon =
  | 'calendar'
  | 'hospital'
  | 'heart'
  | 'work'
  | 'shopping'
  | 'other'

type Event = {
  id: number
  title: string
  date: string
  member: Member
  isAllDay: boolean
  startTime: string
  endTime: string
  memo: string
  icon: EventIcon
}
```

### 6.1 各項目

- `id`
  - 予定を一意に識別するID
- `title`
  - 予定タイトル
  - 必須入力
- `date`
  - 予定日
  - `YYYY-MM-DD`形式を基本とする
- `member`
  - `me`または`wife`
  - 自分・妻のどちらの予定かを表す
- `isAllDay`
  - 終日予定かどうか
- `startTime`
  - 開始時刻
  - 終日予定の場合は空文字列にする
- `endTime`
  - 終了時刻
  - 終日予定の場合は空文字列にする
- `memo`
  - 任意のメモ
- `icon`
  - 予定の種類を表すアイコン

## 7. 予定追加・編集機能

### 7.1 新規追加

- 日付セルのタップで追加モーダルを開く
- 選択した日付を初期値として設定
- タイトル、対象者、日付、アイコン、終日、時間、メモを入力可能
- 保存後、カレンダーに即時反映
- 保存後、データを永続化

### 7.2 編集

- 既存予定のタップで編集モーダルを開く
- 保存済みの情報をフォームへ読み込む
- 内容を変更して保存可能
- 削除可能
- キャンセル時は変更を破棄

### 7.3 入力チェック

- タイトルは空欄不可
- 終日でない場合、開始時刻と終了時刻を入力可能
- 終了時刻が開始時刻より前になる場合は保存しない
- 終日を選択した場合、時間情報は空にして保存
- 日付の形式を統一する

## 8. アイコン要件

予定の種類を、絵文字だけに依存せず、視認性の高いアイコンで表現する。

想定する種類：

- 予定：calendar
- 病院：hospital
- デート：heart
- 仕事：work
- 買い物：shopping
- その他：other

要件：

- アイコンとテキストを両方表示
- 色を増やしすぎない
- アイコンをタップするための独立した小さなボタンを大量に配置しない
- 予定全体をタップできる設計を優先
- 生理の予定など、血液を直接連想させる見た目は避ける
- 妊活関連のアイコンは、必要に応じて後から追加する
  - 例：通院、注射、排卵、検査など
- 無料で利用可能なアイコンまたはSVG素材を優先
- ライセンス条件を確認する

## 9. 妊活向けの拡張要件

将来的に、妊活管理に適した予定種別・記録を追加する。

候補：

- 生理開始日・終了日
- 排卵誘発剤の服用
- 排卵誘発注射
- 通院
- 卵胞チェック
- タイミング
- フーナーテスト
- 妊娠検査
- 体調・症状メモ

注意点：

- 生理アイコンは、血液を直接表すデザインにしない
- 医療情報を扱う可能性があるため、第三者に公開しない構成を優先
- 医療上の判断を行うアプリではなく、夫婦の記録・予定管理を目的とする
- 入力した情報は、ユーザーが後から修正・削除できるようにする

## 10. データ保存

現在の実装方針：

- `localStorage`を利用して予定を保存
- 保存キー：
  - `couple-calendar-events`
- 旧形式のデータが存在する場合でも、欠損フィールドを補完して読み込めるようにする
- ページを再読み込みしても予定が残るようにする

将来的な方針：

- 夫婦2人の端末間で同期する必要がある場合は、サーバー側データベースを導入する
- Cloudflare Workers / D1 / KVなどを候補とする
- データ同期、認証、バックアップ、障害時の復旧方法を設計する
- 医療・妊活関連の情報を扱うため、アクセス制御と通信の暗号化を重視する

## 11. UI・UX方針

- 妻が直感的に操作できることを優先
- 初見でも使い方が分かるUI
- 余白を適切に取り、タップ領域を十分に確保
- スマートフォンの片手操作を考慮
- モーダルは画面内でスクロール可能にする
- 小さい画面でもフォームが画面外に隠れないようにする
- 色を多用しすぎず、落ち着いたデザインにする
- アイコンとテキストの組み合わせで意味を伝える
- 自分と妻の予定は、色だけに依存せず、表示情報でも区別できるようにする
- エラー表示は、ユーザーが原因と対処法を理解できる文言にする

## 13. 現在の既知の注意点・改善候補

- スマートフォンのタップ操作を継続的に検証する
- 日付セルと予定ボタンのクリック領域が干渉しないようにする
- CSSの`pointer-events`や重なり順による操作不能がないか確認する
- アイコンの見た目を最終調整する
- 妊活専用アイコンを追加する
- 予定の並び順を検討する
  - 終日予定を上
  - 開始時刻順
  - 作成順など
- 同じ日に予定が多い場合の表示方法を検討する
  - 「他○件」表示
  - 詳細一覧表示
- 予定の繰り返し機能は必要性を確認してから追加する
- データのエクスポート・インポートを検討する
- localStorageのみの場合、端末間同期はできない
- 本格的なログイン・同期機能を実装する場合は、認証・権限・バックアップを別途設計する

## 14. 開発ルール

Copilotがコードを変更する際は、以下を守る。

1. 既存機能を壊さないこと
2. TypeScriptの型安全性を維持すること
3. Reactのstate管理を分かりやすく保つこと
4. スマートフォン操作を優先して設計すること
5. 予定ボタンと日付セルのイベント伝播に注意すること
6. 変更範囲を必要最小限にすること
7. UIを変更する場合は、PC表示とスマートフォン表示の両方を確認すること
8. localStorageの既存データとの互換性を維持すること
9. 不明な仕様を勝手に決めず、必要なら確認事項として明示すること
10. 実装後は、TypeScriptエラー・ビルドエラー・操作上の問題を確認すること

## 15. Copilotへの基本指示

このファイルをプロジェクトの設計仕様書として扱うこと。

- まず現在のコードを確認してから変更する
- 既存の仕様と矛盾する変更は避ける
- 変更前に、影響するファイルと実装方針を簡潔に説明する
- 複数ファイルを変更する場合は、変更理由を示す
- 完了後に変更内容、確認した項目、残っている課題を整理する
- ユーザーが「全部実装して」と指示した場合は、関連するファイルをまとめて変更してよい
- ただし、認証・外部サービス・課金・データ削除などの不可逆性が高い処理は、実装前に確認する
- セキュリティ、個人情報、医療関連情報の取り扱いに注意する
